# Blast radius（改動既有行為前先盤點呼叫端）

本檔維護規劃階段的影響範圍門檻。`ai-knowledge/share/constitution.md` 保留案例與背景，不另定本項規範。

## 何時強制

改動**既有**共用函式、常數或分支的求值路徑時適用，不限於新增程式碼。三種常見形狀：

- 移除 build type 短路（`isNotRelease()`、`isDebugOrDogfood()`）或其他環境判斷分支
- 改變既有函式讀取的來源（本機 preference 換成 Remote Config、快取換成即時讀取）
- 刪除看起來沒人用的 helper、常數或預設值

「只刪了幾行」不是豁免條件。刪掉一個分支不改變呼叫圖，它改變的是每個既有呼叫端現在走分支的哪一側。

## 硬門檻（規劃階段就要做完）

1. **盤點呼叫端**：對每個被改動的符號跑一次 `rg "<symbol>"`，列出全部呼叫端。本機有 `querying-graphify` Skill 時，再對被改動的**類別**跑一次它的 `affected`，補上匯入、繼承與實作該類別的檔案；方法層級的呼叫端仍以文字搜尋為準，圖查詢只補漏不取代。
2. **判定測試可達性**：逐一問「這個呼叫端會不會在 `src/test` 被求值」。constructor、`init`、default parameter、`object` 初始化最容易漏掉。
3. **列出受影響的既有測試類別**，與新寫的測試並列寫進本次驗證清單。
4. 前三步的結果要落在計畫與待辦清單上，不是寫在背景說明裡。實作時發現漏列的影響，先補計畫並處理範圍／驗證問題，不得以「計畫沒列」略過。

## 新增資料讀取或事件產出

新增 `layoutInfo`、StateFlow 或同一快照的讀取點前，搜尋既有讀取點，比對過濾、座標、時機與前置條件。差異必須有行為上的理由；例如預取與完全可見判定目的不同，不為追求一致而改壞原讀取點。

在共用物件新增事件產出端前，列出所有觸發者與消費者，包含舊版本呼叫端及沒有 collector 的期間。寫清楚無人消費、緩衝滿、取消與重新訂閱時會發生什麼，並把相關驗證列入計畫。容量與狀態／事件選型見 `.agents/skills/kotlin-flow-state-event-modeling/SKILL.md`；單一票接受的無界緩衝不是全專案預設。

## 紅旗

被改動的符號出現在任何 Fragment、ViewModel 或 store 的 `init` 路徑上：把該 Fragment／ViewModel 的既有測試直接列進驗證清單，並套用 `.agents/rules/fragment-lifecycle-tests.md`。

改動共用 UI 容器的顏色或樣式 token，而本次只遷移部分呼叫端：對**未涵蓋**的每個呼叫端回答「這次改動讓它變好、不變，還是變壞」。判定方式是查那個呼叫端有沒有自己寫死同一組視覺屬性，有就是變壞。任一個變壞就硬停問使用者，不准自行以「不在本票範圍」結案；不在範圍不等於不受影響。上面三道硬門檻問的是測試會不會紅，這一題問的是外觀會不會壞，兩者不互相取代。

# Mutation 效力與還原

門檻由 [test-evidence](../../../rules/test-evidence.md) 維護；本檔提供操作與判讀。執行者與工具遵守目前 runtime 及任務授權。Studio 工具對照見 [studio-tools](../../../adapters/studio-tools.md)，不能用另一個編輯器的操作範例擴大權限。

## 先確定測試抓得到目標

記錄要守住的行為、目標測試與預期 assertion。負向結果之前要有正向前置：目標分支已進入、節點曾存在、狀態先為 true，或副作用的必要條件成立。否則預設 false、空資料或匹配不到任何節點也會綠燈。

先跑目標測試取得綠燈；新建或修改的測試類別另外遵守主 Skill 的單類別隔離執行要求。編譯成功與 BUILD SUCCESSFUL 不能單獨證明測試執行：核對 filter、實際案例數與本次結果，排除 NO-SOURCE、SKIPPED、過期 XML 或只命中其他方法。需要效力證明時確保重新執行，而不是沿用快取。

## 改壞前保存基準

保存所有預計暫改檔案的完整內容、SHA-256、是否原已存在，以及當時的工作目錄／staged 狀態。基準是 mutation 前的工作內容，包含尚未提交的實作與使用者改動。多個人或 Agent 共用同一檔案時，先協調避免同時寫入；無法區分後續修改時，不整檔覆蓋。

`git diff --exit-code` 預設比工作目錄與 index，不是與 mutation 前的內容比對。它可以因既有未 staged 的改動而回非零，也可以在 staged 內容仍有變更時回零。因此不能拿它當通用還原證明。

## 紅燈必須來自預期行為

只改壞要驗證的行為，保持目標 assertion 不變，用同一 filter 重跑。從本次 JUnit XML 記下失敗方法、assertion 與預期／實際值。語法或編譯失敗、全域服務尚未初始化、其他測試失敗，均不算效力證明。

原則上一次改壞一個行為。不同事件分輪驗證，特別是「先設 flag」與「再清 flag」；同時移除可能讓負向 assertion 永遠看見預設 false。若懷疑同一事件有互相替代的觸發點，可以先移除整組確認測試會紅，再逐一恢復查明作用；不得把不同 lifecycle 事件混成同一組。

## 沒變紅時

先確認測試真的重跑、mutation 真的生效、前置與時間推進正確、改壞的分支可達。再檢查 matcher／觀測盲點、替代觸發點與等效改動。記錄未排除的原因，修正實驗後重跑，不把綠燈直接解讀成死碼。

刪除冗餘行為需要另外證明其他呼叫端、時序與 lifecycle 不依賴它，並遵守影響範圍與核准要求。單一測試拿掉某段仍綠，只能描述該測試下的結果。

## 還原與完成

只還原本輪暫改內容，不重設整個工作目錄或 index。逐檔比對保存的內容或 SHA-256；另外檢查 mutation 新增的檔案與暫時標記。確認原有未提交改動仍在、沒有覆蓋其他人的新修改。沒有暫時標記及重跑綠燈可以輔助，不能取代內容比對。

若已逐位元還原到剛才綠燈的相同內容，且沒有環境／相依改變，不強制第三輪；無法確認相等或環境已變，重跑後仍須說明還原比對結果。還原失敗或不確定時立即揭露，不宣稱完成。

回報記錄至少包含：行為宣稱、正向前置、測試 module／filter、綠燈結果、暫改內容、預期 assertion 的紅燈結果、還原基準與比對結果。既有歷史紀錄只保留當時真正做過的檢查，不倒填快照驗證成功。

## Compose matcher 案例

`hasTestTag(t) and hasText(s)` 對同一節點套用兩個條件；容器有 tag、子節點有文字時可能永遠匹配不到。跨層尋找用 `hasText(s) and hasAnyAncestor(hasTestTag(t))`，並確認所選 merged／unmerged 語意樹。`onChildren()` 只處理直接子節點，不能當所有子孫。

review 找到問題、寫了修正、測試綠燈是三個不同觀測；修正有效仍須自己的紅燈證明。
